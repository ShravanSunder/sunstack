The kind filter: what the experiment found, and three decisions

You asked for the kind filter to be built with Jev properly and decided by experiments and data. The Jev Advisor ran them: all 78 skills, blind labels from two independent labellers, three designs compared, bars set on one part of the data and checked once on a held-back part. 253 Jev calls, $0.011 in total. Every request and answer is kept.

One well-written question with five answers beat both trees. With its bar at 85%, it made no wrong calls on the held-back skills (14 right, 1 unsure). So the engine's filter stays one question; it doesn't need a decision graph. Three things are yours to decide below.

What was tested

Three designs, each fully written before any run:

Each design's bar was set on 56 development skills so that it made no wrong calls there. The bars were then frozen, and only then were the 15 held-back skills run:

Design (frozen bar)Development: right / wrong / unsureHeld-back: right / wrong / unsure
A · one question (85%)30 / 0 / 2614 / 0 / 1
C · two steps (80% each)29 / 0 / 2712 / 0 / 3
B · tree of 5 yes/no (65% / 35%)10 / 0 / 466 / 0 / 9

Why the tree lost: an early yes/no question that is only moderately sure stops the tree, even when a later answer is clear. Example: for the agentstudio skill, "tool manual?" was 88% yes, but "repo-specific?" was 64%, so the tree said unsure. Both trees also wrongly called the new domain-code-standards skill "general", where the one question stayed unsure.

The one question's five answers, as Jev was asked them: general (a reusable workflow, practice or judgment across repositories), role (a standing job in an agent team), domain (a subject's reusable standards), tool_manual (operating one named tool through its interface), repo_specific (one repository's own procedures). Each answer's full criteria are in the report.

1. How strict should the bar be?

The bar is how sure Jev must be of one answer before the rules use it. Below the bar, the skill is skipped and listed, never silently passed.

BarDevelopment (56 skills)What it costs
85%30 right, 0 wrong, 26 skippedabout half of skills skipped and listed
70%45 right, 3 wrong, 8 skipped3 skills given the wrong kind

The 3 wrong answers at 70% were all inside the same group: a role or domain skill called general, or the reverse. None of them changed whether the general-skill rules run. They would matter to a future rule that cares about the exact kind.

2. Should Jev read more than the description?

From the description alone, Jev misses what domain skills are for. Example: domain-typescript, description only, gave general at 50%. With the first 1,800 characters of the skill's body added, it gave domain at 85%. On the 6 hardest skills, the one question got all 6 right with the body added, at the 70% bar. That's 6 skills, not the full set.

The cost: the engine's filter reads one field today. Reading the description plus the opening needs a small, generic change: the filter reads two named fields. That's not a decision graph.

3. Five skills where the labellers disagreed

Two independent labellers agreed on 71 of 76. These 5 split. Your answer becomes the right answer in the permanent test set. Until then they're left out of the accuracy numbers.

What is still not proven

  • No real repo_specific example. None of the 78 skills is clearly one repository's own procedure. The next test set adds sunstack-tools' verify-sunstack-rule and verify-demistify, labelled blind.
  • Jev's answers move a little between identical runs. In one repeat, an answer went from 77% to 80%. That's why the bar sits at 85%, not just above 70%.
  • The engine path isn't built yet. These were direct Jev calls. The real filter (one question per folder, gates before a rule's first step) is proven when deliverable 1 is built, with this data as its permanent test cases.
