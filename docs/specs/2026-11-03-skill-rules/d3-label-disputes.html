Five pieces of skill text: how should the rule treat them?

A skill meant for every project shouldn't contain one specific product's own steps: its own commands, files or debug loops. Example: ops-observability-stack line 17 says "if you're debugging AgentStudio, follow AgentStudio's own debug loop". That belongs in AgentStudio's repo, so the rule should warn there.

Questions 1 to 4: should the rule warn or not warn on this text? Question 5 is different: both answers mean no warning, and it only decides how the text is filed for testing. My suggestion is marked on each. Replying "agree with all" is enough.

1. presentation-html loads Demistify's guide

MUST load the guide for the page's binding
(https://demistify.getagentstudio.dev/v1/authoring/SKILL.md)

In plain words: before writing a page, read Demistify's guide from its website. Demistify is the page tool you use for every page.

2. presentation-html runs Demistify's command line

use the CLI at the page's binding:
pnpm dlx https://demistify.getagentstudio.dev/v1/demistify-cli.tgz embed …

In plain words: build the page with Demistify's own command. Same tool as 1, a command this time.

3. scaffold-project runs its own script

Run the appropriate scaffold scripts:
bash ${CLAUDE_PLUGIN_ROOT}/scripts/scaffold/scaffold-project.sh --name "project-name" …

The script ships inside the same plugin as the skill.

4. practices-verification finds a project's verify-<app> skill

List .agents/skills/verify-*/SKILL.md in that project …
Resolve .claude/skills/verify-<app> …

<app> is a blank to fill in, not a real product. Both checking agents said warn.

5. audit-security-review loads its own reference

MUST load references/routing.md before preparing a prompt …

Both checking agents said: don't warn. They disagreed only on how to file it for testing the rule, as an ordinary example or as a near miss. Either way, agents see no warning.
