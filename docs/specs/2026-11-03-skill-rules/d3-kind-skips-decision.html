What goes wrong today

Before a general-skill rule runs on a skill, Jev reads that skill's description and says what kind of skill it is: a general workflow, a role, a subject's standards, a manual for one tool, or one repository's own procedure. If Jev is below 70% sure (70% itself is enough), the rule skips the whole skill. A scenario is a real passage of skill text with the right answer written down; under the current adoption rule, you adopt a rule only when it gets every scenario right.

A real example. peekaboo is a manual for one tool, the Peekaboo command-line app. Its description reads: "Use when testing, inspecting, or automating native macOS UI with Peekaboo, or its Screen Recording or Accessibility permissions…". That sounds like a general testing workflow, so Jev says general at 0.55 and is unsure. Five scenarios check that the rule stays quiet on Peekaboo's own commands, which a tool manual is allowed to teach. One of them is this passage from peekaboo/references/troubleshooting.md: under "Accessibility permission required", the fix is peekaboo permissions status. Expected: the rule says nothing (not applicable: a tool manual). What happens today: the skill is skipped, so the scenario never runs. A description that starts "Use when operating the Peekaboo CLI…" says what the skill is.

The other two:

  • domain-decision-models holds the standards for decision models, but its description lists tasks ("Use when designing, changing or reviewing a decision model…"), so Jev reads a workflow at 0.58. One scenario.
  • practices-verification-maintenance: you labelled it "one repository's own procedure". Still open with you: is a practice that builds a project's own verification setup "one repository's own procedure" (what it produces), or a general practice (it works in any repository)? (question 3 on the round-2 page). Jev reads general at 0.63, below 70% either way, so its description needs to say which it is once you've answered. One scenario.
