# Lean role guidance — specification r1

## Obligations

- S1: Management defines only Exact Steps and Designed Outcome for task guidance and preserves work levels/horizon and actual contract span without requiring a repeated classification recital.
- S2: Designed Outcome implements the supplied design docs; the executor chooses detailed execution, and changed governing expectations/contracts/ownership return to Lead with evidence.
- S3: Implementation uses Terra high Local, Sol medium Cross-domain, Sol high Cross-domain/Cross-system, Opus medium Cross-domain, or Opus high Cross-domain/Cross-system, all Designed Outcome.
- S4: Verification has no guidance selector and uses Terra high Local/Cross-domain, Sol medium Cross-domain, or Sol high Cross-system, with no Opus row.
- S5: Review retains its independence and admission rules and uses Sol high or Opus high; existing assigned sessions retain their model/effort.
- S6: Operator is always Exact Steps/Luna high with no span column and is encouraged for inexpensive prescribed support when the handoff is worthwhile.
- S7: Implementer and Verifier select native helper models from the relevant catalog by each bounded task's own span within the actual grant and host capability; a child gets relevant sources, permitted effects and an ending check, and its parent inspects and integrates the result.
- S8: A Verifier's helper may perform separable observations or granted apparatus work, but may not repair product code/tests, change the oracle, or independently verify implementation it authored.
- S9: Catalog guidance notes Terra and Sol for browser/computer control without changing effort/span eligibility, implying tools exist, or claiming measured superiority.
- S10: Active examples, provider manuals, README and nested AGENTS agree with the new map, while schemas, role/files transport, proof, acceptance, review and 55-minute source cadence remain unchanged.

## Transfer checks

| Rule | Different valid setting | Bad choice the rule rejects | Verdict |
|---|---|---|---|
| S1–S2: implement supplied design, choose steps | Rust storage implementation and Swift UI implementation both choose internal steps under settled contracts | An agent changes an HTTP response contract because internal coding is easier | Pass |
| S3–S7: select by actual task scope and permitted model | A Cross-system deliverable contains a Local parser subtask routed to Terra high | Calling the whole deliverable Local because each helper edits one file | Pass |
| S6: prescribed support returns observations | CI watch and transcript extraction both follow defined criteria | Luna independently repairs an authentication failure or interprets owner intent | Pass |
| S7–S8: parent owns combined result and grant | Independent UI journeys and disjoint driver repairs can run concurrently | Two helpers reset one shared fixture, or an author grades its own product as independent proof | Pass |
| S5, S10: acceptance then outside review | A CLI delivery and browser delivery both need Lead's own acceptance | A Lead forwards a green summary to a Reviewer as a substitute for acceptance | Pass |
| S9: fit capability to assignment | Browser verification and native computer-control checks use actual available tools | Treating model preference as evidence that a browser or desktop grant exists | Pass |

Named models are the owner's adopted policy scope, not universal model rankings. Runtime wording keeps the policy once in management; roles load it rather than copy its table.
