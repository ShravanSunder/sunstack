## The dogfood run, and what it shows

After the runs land: the runner on every skill-authoring skill. It shows the eight rules assemble across the two RuleSets, the two metadata rules complete on every `SKILL.md` and nowhere else, and every skill's description starts with `Use when` within 1,024 characters, or names the one that doesn't. The `prepare_rules` proof run then shows where the judged rules would ask their questions, file by file. Then the unit's implementation review runs: a fresh `skill-review` implementation review that loads the branch's `skill-review` after run 4, so its new first pass runs the rules on this change's own files, by reviewer agents whose host records show which copy they loaded and the native report they consumed. Review R1's reading of milestone 1's copy proves only the design route, not this integration.

## Behavior, and what stays unverified

- This change is the next real skill change through milestone 1's lifecycle, so the review and the runs are the owner's chosen behavior proof for milestone 1: agents designing, reviewing and writing with the new skills, read from their records. A commission that names the skills to load is guided use, not an unprompted behavior run (`proof-claims.md`), and is reported as such.
- Unverified until later: how a hosted judge answers the six judged rules (evals, unit U4); whether the orchestrator's and audit's sites work once switched on; whether `prepare_rules`' plan matches what a hosted evaluation sends.
