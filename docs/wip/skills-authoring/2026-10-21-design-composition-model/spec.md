# Design composition: Markdown and pages that people can read

This spec proposes how design documents are composed so that people, not only agents, can read them. It covers the Markdown layout and chunk shape, the page as the default way people read a design set, concept views, reading paths, who builds the page, and keeping pages fresh. It continues `../2026-10-21-presentation-html-authoring-depth/spec.md`, which covers page authoring in `presentation-html`.

Status: **proposed, design open.** The owner's directions below are settled; the open questions at the end need owner decisions before runs are fixed.

## Open questions

1. **Chunk default per document.** Should capability chunking be a presumption that the existing split test confirms for each document? Requirements and Specification usually split cleanly by capability. Program Design and Verification Design often stay whole, because one component or observation serves several capabilities (`design-documents.md:29`). The Worked Set and spec-design `references/artifact-and-self-review.md:32,36` must then change to match, as must the review lane `lanes/artifact-navigation.md:22-29`, which flags "tiny-file sprawl".
2. **Shared chunks.** Which shared chunks exist, and which fact owns each? Every R row keeps one home capability (`design-documents.md:40`), and a cross-cutting obligation lives with the need that asked for it (`artifact-and-self-review.md:34`). Where do the capability list and the shared Verification observations live once Requirements and Verification Design become folders?
3. **Capability list.** `discuss-pathfinding/references/user-requirements-extraction.md` writes the list first, as `key: purpose`. spec-design's capability map (`SKILL.md:282`) re-renders it, with the owner's name, "also serves" links and an area level. Is the nested-list tree the list itself, or the map in Markdown? Pathfinding is then a caller that must cut over.
4. **Naming.** "Journey" already means two things: spec-design's journey map, and verify-app journeys in verification-design. Name the order dimension **reading path / through-line**, as `design-documents.md` already does.
5. **Concept views.** The page side already takes a default in presentation-html's D26: a concept section built from links, selected when obligations in two or more capabilities name the idea or the owner names it. If concepts get a Markdown home here, the page renders that home instead. Do they live in `index.md` as link sections? Is a concept selected when obligations in two or more capabilities name it, or when the owner names it? Is the phase that writes the owning entry the one that updates the view? Is the picture a link, with a missing picture stated as a gap? Which vocabulary row and test update does `docs/diagram-vocabulary.md:48` require?
6. **Chunk shape.** "Human part first" must use the views whose predicates fire, not "one view". Agent detail is rationale, evidence, exact shapes and examples, never conditions, thresholds or error cases. Choose one collapse form, whose summary names the failure cases inside. Keep the binding, trace and call-path tables visible (program-design `artifact-and-self-review.md:103,115`), and keep the rationale people need (spec-design `artifact-and-self-review.md:101`).
7. **Where phases apply it.** spec-design `:115`, program-design `:89` and verification-design `:39` load `design-documents.md` and return identities only. They must also return the set layout, chunk shape and `index.md` duty. This needs edits to spec-design and program-design, which the owner allowed.
8. **Set root and page ownership.** Who owns the design set's root folder (orchestrator-design `:55`, spec-design `:113,248`, program-design `:87`)? Whether a page exists stays the rendering reference's choice. Only then can the phases' duty to create and refresh `index.md` and the page be stated. A shared reference names no phase except as a consumer.
9. **Freshness for live pages.** Every current result is embedded-only (`diagram-rendering-and-fallbacks.md:56,106,118`; docs-maintain `:77,81`). A live `src` page needs its own result: a recheck of derived views. An edited `index.md` whose paths a page renders must trigger it too.
10. **Requirements-only runs.** Should the page default cover a Requirements-only spec-design run (`spec-design:91`)?
