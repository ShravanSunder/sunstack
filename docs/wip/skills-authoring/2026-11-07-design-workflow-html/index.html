Design as HTML: the change to the four-document workflow

This change makes every design the owner's set of linked document pages, built on the components he designed in the lab: on every document page the requirement browser (needs grouped by capability, one need's Overview, Specification, Program Design and Verification views, and the related-documents workspace), and the call-stack browser from a call to the need it serves. Each phase writes its own page: its text in sections and record bodies at stable IDs, with Markdown islands (blocks of Markdown text placed inside a page) where Markdown carries the text best, and one record per need, obligation, design part, check or call path naming only what it serves; preparation checks the set and derives every reverse link. It changes nine sunstack-dev skills, one run each, in order: orchestrator-design (with the design-set contract and the deliverable stage), presentation-html (with the page medium), spec-design, discuss-pathfinding, program-design, verification-design, spec-program-review, docs-maintain and plan-implementation (with the plan record). No run starts until the Demistify Lead releases the browsers, their record contract and preparation; that Lead has taken everything the workflow needs into its draft. The owner has answered: agents read the pages directly, the skills change once at that release, and the success definition is what he wants. The revision's design-review corrections (the security decision for the preparation step; how call frames name the need they serve) are made here for verification; nothing is implemented, and no run starts without the release and his go.

The four parts, in order

  1. Requirements: what the change is for, in the owner's words, and its success definition.
  2. Specification: what the changed skills must do, and the standards they state.
  3. Skill design: which skill changes where, in which order, and the decisions taken.
  4. Skill verification: how each part will be shown to hold, and what stays unverified.
