Batched delivery rounds

This change edits nine skills so that the expensive steps of delivery (the Verifier's observation, the independent review and the Lead's assessment) run once per batch of work instead of once per change. Nothing is dropped: every observation, review and proof still runs, and whatever a batch touches is re-checked.

What changes

The codex-router Lead lost a day because every small fix got its own Verifier pass and its own review, and its stacked PRs had to be rebuilt after each lower change. The skills told it to work that way. The fix collects a round's corrections into one batch, builds once, checks once and reviews once.

A review returns three findings. Each fix gets its own build, Verifier pass and review.

The same three findings become one correction pass at one commit, observed once and re-reviewed once by the same reviewer.

What counts as a batch

A batch is the work between two observation points. It ends at the first of these:

  • the end of the helper's assigned set of work;
  • an observation the plan requires before dependent work can start, such as a Verification Design check or an integration gate inside the assignment;
  • every accepted finding from one review result, applied together at one commit.

One PR can hold several batches. Local tests and integration gates keep their timing. A Verifier target stays fixed while it is being observed.

What you'd see happen

  1. A review returns four accepted findings. The Implementer applies all four, builds once, declares one Verifier target, and the same reviewer re-reviews once.
  2. An Implementer hits three failures inside its slice. It fixes all three and declares one new target after the last fix, not three.
  3. A feature has dependent parts. The plan keeps it in one PR unless you asked for a split or one PR would be too big to review in one pass. Dependent work joins by merge, not by restacking.
  4. An Implementer's commission tells it to stop only for a design break, a public-contract change, your decision or something destructive, and to decide and record the mechanism choices inside the plan. An Operator watching CI that meets a failure its procedure doesn't cover still hands it back rather than fixing it.
  5. A Lead receives six progress messages from helpers. It relays none of them to you, and acts when a batch completes or a helper is blocked.
  6. An assignment has slices A and B, and the plan requires an observation of A before B starts. The Implementer closes a batch after A and waits for the observation. With no such requirement, A and B are one batch.

Why it happens today

The step-by-step skills repeat their cycle for every change, and nothing defines a batch. One rule contradicts its own file: implement-plan sends every completed slice to review, while the same file, the orchestrator and the agent-management skill all review only the finished deliverable. The principle about accepting evidence already allows reusing proof that a change didn't touch; the procedures override it.

Your corrections never reached the skills. They live only in the codex-router project's memory. The skill-failure log has no entry for them, and skill-audit only reads memory for the repository it audits.
