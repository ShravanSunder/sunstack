skill-rules systems: design set

This change teaches agents to build a checked rule, or any set of questions a model answers for code, as a decision model. Each part is its own design: the evidence, single-proposition questions, a tree that code walks, a policy chosen from labelled costs, and proof against a baseline. Three skills carry it:

  • domain-decision-models (new, hidden, sunstack-dev) holds the practice;
  • skill-rules (rewritten, skill-authoring) runs the workflow;
  • decision-model-review (new, sunstack-dev) reviews a model with checks that can fail.

Two routing lines, in skill-review and implementation-review, send decision-model changes to the review. The orchestration design says how they fit together.

The design was validated by the Advisor, accepted by the Lead and reviewed (verdict great), and the skills are written. This change's proof is static checks, the keyed rules self-check with its dispositions, and the reviews. The behavior comparison is a later step the owner plans, not run in this change; its plan stays in skill verification.

The decisions are in orchestration §9, with O4's analysis in skill design.

Reading the set

  1. Orchestration: the flow from a standard to a shipped rule, with who owns each step and which gate can fail. Start at §3.
  2. Requirements: why the change, in the owner's words, and what success looks like.
  3. Specification: every obligation and standard as one sentence, with its transfer cases.
  4. Skill design: what each of the five runs writes.
  5. Skill verification: how each part will be shown to hold, and what won't be.
