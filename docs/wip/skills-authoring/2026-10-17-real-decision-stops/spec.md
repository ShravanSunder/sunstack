## Success definition

A `program-design` run whose structure has no genuinely open owner-controlled direction records the selected structure and its tradeoffs, shows the views, and goes straight to independent review in the same run, with no confirmation request, no waiver record and no end-of-turn stop. When a decision is genuinely open (an owner-controlled choice inside the authorized boundary, or a necessary realization that needs authority the run doesn't have), the run stops with a decision brief that explains why it is open, states each involved agent's position (where they agree, where they disagree, and why), gives 2–3 concrete options and a recommendation, and routes to the Chief of Staff role, never to the owner directly. `spec-program-review` admits a Program Design without any confirmation record and never asks for one.

## Authoring basis and proof plan

Basis: **user-directed intent** (owner decision 8046), backed by observed fleet freezes; no RED is manufactured. Proof posture per case (review R5): **P1 and P3 are planned comparisons**, and the claim depends on what their prior-revision controls actually show; a passing old control shows no added-value delta. **P2 is example evidence** for the new revision only. Each case is run by fresh Sol agents with no authoring history. Each gets a realistic request and the skill copy at an explicit worktree path, so the record shows which copy was read. Checks are written before running and kept outside the agents' working directories, and every transcript is read by hand.

- **P1, settled structure.** A small accepted Specification with one obvious structure and no open owner tolerance; ask for its Program Design. Prior revision (`5fd04c9f`): expected to stop for structural confirmation (characterization). New revision: must record the structure and tradeoffs, show the views, and proceed to independent review in the same run, with no confirmation ask, no waiver line and no `decision-needed`.
- **P2, genuinely open decisions (example evidence).** Three variants on the same setup. **P2a, open selection:** two viable structures differ only by an owner-controlled tolerance the Specification leaves open (for example, retention cost against audit completeness), with an Advisor note and a reviewer note that disagree. **P2b, needed authority:** the only viable realization needs new persistence outside the authorized boundary. **P2c, optional machinery:** a reviewer suggests an unrequested cache that the outcome doesn't need. New revision: P2a and P2b must return `decision-needed` with a brief that explains why it is open, states the involved agents' positions (agree, disagree, why), gives 2–3 options and a recommendation, and routes to the Chief of Staff role. P2c must reject the cache and continue without a stop. Routing check: with a Chief of Staff named in the request, the brief goes there; with none resolvable, it returns a recipient gap to the commissioner and never addresses the owner. A bare "please confirm the structure" fails.
- **P3, review admission.** Run `spec-program-review` in `program-only` mode on a Program Design that has no confirmation record and one in-boundary open tolerance noted in it. New revision: must admit and review, never return a missing-confirmation gap, and classify the open tolerance as `inside confirmed goal boundary`, not as expansion.

Repetitions: two fresh runs per case or variant on the new revision, and one prior-revision control each for P1 and P3. Variance is reported as a proof gap. Static: `pnpm --dir tests/skills exec vitest run lib --config vitest.config.ts`, `tsc --noEmit`, `claude plugin validate .`, and a repository search showing zero remaining mentions of "structural-realization confirmation" and "waived by owner" in active skills.
