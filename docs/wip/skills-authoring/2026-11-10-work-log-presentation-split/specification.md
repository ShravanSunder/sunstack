# Observable obligations

- S1: Logging runs without loading rendering instructions, creating page summaries, writing HTML, or making a page a completion condition.
- S2: The renderer requires an explicit owner request naming a work-log page or explicitly naming the rendering skill; a generic progress or log request is insufficient.
- S3: Each request authorizes its requested creation/refresh only, not an ongoing update loop.
- S4: Logger entry, checkpoint, fallback, reconciliation, UI metadata and completion paths preserve S1.
- S5: Requested rendering reads the log through a stated cutoff and keeps author, authority, closure, coverage, acceptance and uncertainty distinctions.
- S6: Four ordinary h2 sections carry decisions, progress, changes/reasons, and checks/misses; presentation-html selects explanatory prose, diagrams, tables, traces, code and disclosures without mandatory Story boxes or rows.
- S7: One maintained owner holds each rendering procedure and Story-summary shape; historical log rows remain readable and unchanged.
- S8: Existing generic presentation-html and frozen workflow-v1 files remain unchanged.

Transfer: a multi-day implementation checkpoint and a no-board investigation both log without HTML (S1/S4); a requested incident page and an explicitly requested refresh both render once (S2/S3). An unresolved assumption and a second-hand proof both remain qualified in the page (S5). A message custody sequence and a filter comparison can use different supported views under the same headings (S6). A legacy Story and a new proof row keep their existing identities and closure semantics (S7). These cases preserve the intended boundaries.
