# Required authoring behavior

1. Preserve the historical engineering guidance on authority, domain entities and identity, invariants, observable contracts, ownership, boundaries, state machines, failure/concurrency and meaningful verification while using current v2 skill names and dependency paths.
2. Keep Requirements, Specification, Program Design and Verification Design separately identifiable, with complete HTML text and one authoritative home per fact.
3. Organize Requirements into meaningful named capability groups visible in normal reading order, using smaller grouped tables or headed requirement sections as the content warrants, without inventing extra capabilities for a one-concern set.
4. Use shared navigation JSON for a v2 design collection's Pages, semantic Map and complete question-led Walkthroughs through the matching guide's existing contract, including only pages and destinations that exist.
5. Make Map groups target their visible group context and needs target their actual text, with useful subject titles/descriptions and related links to owning rules, design and proof, without forcing a four-stage tree beneath every need.
6. Keep normative prose, conditions and diagrams in HTML while JSON owns navigation metadata and references rather than a second need/rule/check corpus.
7. Explain each material journey beside its appropriate diagram, including purpose, important transitions, outcomes and failures, with the owning phase's required semantic fields and no invented pain, current behavior or approved policy.
8. Select general components by reader question, retain call stacks only with real source-derived paths and their required prepared data, and exclude the specialized requirements/stage projections from new free-form designs.
9. Keep governing conditions, invariants, failure obligations, risks, proposals and unknowns visible while putting optional supporting detail behind descriptive disclosures.
10. Explain choices and open discussions with worked examples that distinguish a recommendation, a local reader selection and an actual owner decision.
11. Reconcile changed meaning and approval status across owning passages, summaries, diagrams, navigation metadata and planned proof without silently deciding an unresolved contradiction.
12. Read the matching bound guide for syntax and delivery, preserve v1 Markdown compatibility, and report unavailable matching shared-navigation support or HTTP-fetch requirements without substituting invented standalone behavior.
13. Check markup, actual destinations and collection search freshness, then inspect complete content through concrete reader questions, using an independent reader when commissioned or required by the governing review, while keeping source/content evidence separate from rendered appearance and product behavior.

Transfer cases: a Rust delivery service can group needs around responsiveness, recovery and operator visibility while its implementation follows ownership; a Swift document editor can group needs around editing, saving and recovery while its journeys show user-visible transitions. A shared rule has one home even when several groups link to it. Neither case requires matching headings across all four documents or one decorative component per record.
