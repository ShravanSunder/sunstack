### 2. Matt’s testing references needed their own read

The earlier source note demonstrated full main-file reads, not a complete recursive read of every linked reference. Two labels in the pasted tree, `writing-good-tests` and `mocking-at-system-boundaries`, resolve to [tdd/tests.md](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/tdd/tests.md#L5) and [tdd/mocking.md](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/tdd/mocking.md#L3). They are supporting files, not standalone SKILL.md entrypoints.

The follow-up read supplies three useful specifics. Assert consumer-visible behavior through the intended interface so internal refactors do not invalidate the test. Derive the expected answer independently from the contract; recomputing it with the implementation’s algorithm can produce a test that passes by construction. Keep external assumptions visible: boundary mocks can isolate an external API, but mocking the interaction being changed defeats its proof. Matt also favors dependency injection and operation-specific interfaces over a generic fetch function that forces conditional mock behavior.

Those are good source examples, not blanket local bans on call assertions or direct storage observations. If a protocol sequence or stored effect is the actual contract, it can be the right oracle. The local standard asks whether the selected test can observe the obligation and fail when it is broken. Existing plan/review source already encodes independent oracles and mock-boundary false-green risks; this follow-up does not establish how reliably agents apply them.

## How to write a good SDLC skill from these lessons

Start with the behavior that keeps failing or the repeatable need that makes the skill useful. A topic such as “testing” is too broad to tell an agent when to load it. A trigger such as “Use when selecting proof for a planned behavior change, especially when a mock could hide the changed boundary” identifies a decision and a failure symptom. State the adjacent work it does not own so it does not become a second planner, implementer or reviewer.

Write the mental model before the checklist. For a proof-selection skill, the model is that every test is a claim about an observable obligation; the cheapest test is useful only if it can observe that obligation. That explains why a unit test can be sufficient for a calculation and insufficient for a cross-process handoff. It gives the agent judgment for cases the checklist did not enumerate.

Then write the route and the exit checks together. “Inspect existing tests” is weak because an agent can read a filename and move on. “Identify the assertion that fails when the required effect is absent, and name any mocked interaction that would hide that absence” demands the legwork. A completion criterion should both distinguish done from incomplete and require the work necessary to make that distinction.

Put mechanics in the existing executable owner where possible. The skill should know how to find and interpret the command; it should not repeatedly invent setup scripts. A bundled helper is useful when stable mechanics are otherwise reconstructed badly, but it needs documented invocation, failure semantics and real execution proof. A generated verifier that has never been run remains a draft. Pstack’s [creation](https://github.com/cursor/plugins/blob/ecc249f1e306fc64ddf83c7bed16cacf7c2239db/pstack/skills/create-verification-skill/SKILL.md#L38) versus [maintenance](https://github.com/cursor/plugins/blob/ecc249f1e306fc64ddf83c7bed16cacf7c2239db/pstack/skills/maintain-verification-skill/SKILL.md#L29) is a concrete example: prove one feature when creating it, then cover every admitted mapped feature during upkeep.

Keep the all-run route, decisions, invariants and completion boundary visible in SKILL.md. Put a platform recipe or uncommon branch behind a conditional reference. Give that reference a precise load condition and a result the caller uses. A reference that says only “be careful” or repeats output labels adds little; it should teach what to inspect, good and bad cases, and when to stop. The main path should remain understandable without recursively opening the whole skill tree.

Choose steering from observed failure. Use a required output slot when the agent omits an element; use a sharper predicate when it takes the wrong branch; use a bright-line rule with the actual excuse when it knowingly skips a check. “Worker said done” should lead to “open decisive source and proof before accepting,” not another generic paragraph about thoroughness. Do not manufacture an anti-rationalization table merely to resemble a source pack.

Prove the skill under pressure. A fitting scenario should make the tempting shortcut available, then observe whether the skill changes the choice. Include a negative control where the skill should not load or where a narrower check is sufficient. Keep scenario, source identity, model/effort, observations and grader criterion together. A plausible answer, a parsed receipt or a higher aggregate score does not prove the desired behavior. Repo-required pressure scenarios and evaluation commands still govern any later runtime edit.

Finish with a small output contract: the established result, decisive evidence, unresolved assumptions and next owner. Do not require a large ledger to restate every step. Match proof to the affected behavior and keep public artifacts separate from private session material. Prune sentences whose removal changes no necessary behavior, and repeat measurements only when a change, failure or unresolved concern warrants it.

## Lead validation remains part of the work

The hierarchy does not require the Lead to become the implementer. The Sidekick implements and produces fitting proof. The Lead owns the substantive acceptance check: inspect the changed source, compare the evidence with the original need and plan, challenge weaker substitutes, and return unproven work for correction. Independent review follows that assessment; it does not replace it. Worker completion is evidence intake, not automatic acceptance.
