# Implementation Goal Orchestration

An implementation goal stays with the orchestrator, who remains the default user conversation and owns design decisions with the user, every governing design and implementation-plan artifact, the coordination root, cross-PR integration, disposition, acceptance, and the final report. After a Lead-authored plan is ready, each workstream gets one persistent pair: a 🐒 Implementer, who owns its implementation, associated proof, and corrections, and a 🔬 Verifier, who proves the delivered behavior independently on the real surface. A workstream is one planned PR assignment, or a dependent stack of them, as the plan and the org's rules give it. The user may explicitly choose direct contact with an Implementer inside its scope without changing execution ownership or governing authority. An independent persistent 🔎 Reviewer examines implementation only after the orchestrator has assessed completed development, proof, and the Verifier's report.

## Execution Responsibility

Before planning, use the current goal context or applicable handoff and the next phase's existing input/result contract. The orchestrator loads `plan-implementation` itself and authors the plan. Only after that plan identifies its PR assignments, group them into workstreams and MUST load `manage-agents` to commission or resume one 🐒 Implementer and one 🔬 Verifier per workstream, and return each one's responsibility, continuity, workstream boundary, prerequisite, exact execution root, and user-conversation route. The Lead remains the default conversation unless the user explicitly chooses direct contact with an Implementer. The orchestrator keeps the coordination root plus every execution root as `orchestrator`. Each workstream has one execution root: its Implementer joins as `implementer` and its Verifier as `participant`. At commission, apply and verify the `manage-agents` `<emoji> <role> · <purpose>` title, or report the title capability gap. Seats describe thread participation rather than authority; `practices-collaboration` owns the complete role-to-seat mapping.

Each 🐒 Implementer executes its workstream's changes and associated proof directly by default, and shares facts with its 🔬 Verifier directly. Any delegation either makes goes through `manage-agents`. For agent-router delivery, use `agent-collaboration`; roots are linked through existing message references rather than a new hierarchy mechanism.

## Orient the Goal

1. Establish `requested terminal: plan-only | pr-ready-unmerged`; default to `pr-ready-unmerged` unless the user supplied a narrower terminal, and pass that terminal to the planner, which receives it from its caller. Merge is a separately authorized extension through `implementation-pr-wrapup`, never an inferred terminal.
2. MUST invoke `practices-show-me-your-work` and return the shared work reference (or explicitly unshared checkpoint path) plus responsibility for the whole work or a contribution. Reuse supplied work context for nested work. The tracker owns continuity, fallback, conditional views, and deliberate thread resolution.
3. MUST load `references/goal-contract-and-routing.md` and return the current orientation, admitted basis, next owner or exact stop, and finish decision.
4. Read current repository instructions, relevant source and diff, governing artifacts, plan, proof, and review evidence. Use the trail to find evidence, then verify current facts at their source; a historical result is context, not current proof.
5. MUST load `../../shared-references/phase-return-tokens.md` and map a returned token to its next owner: `requirements-gap` -> `discuss-pathfinding`; `specification-gap` or `program-design-gap` -> `orchestrator-design`; `plan-defect` -> the planner named in the plan's `originating planner` field (`plan-implementation | plan-improve-repo`); `ready-for-implementation` -> `implement-plan`; `ready-for-review` -> `implementation-review`. A design cycle hands back a `CycleReturn` from `orchestrator-design`: `ready-for-planning` -> `plan-implementation`; `stopped` -> load `../../shared-references/owner-decision-brief.md` and return the brief. Mapping names the next owner; it never widens the requested task or terminal.

## Carry the Delivery Loop

1. Decide reversible, in-scope calls yourself and record each as a decision through `practices-show-me-your-work` instead of asking; ask only when the call would change a public contract, persisted data format, or ownership. The Lead remains the default user conversation. The user may explicitly choose direct contact with an 🐒 Implementer inside its scope. In either branch, the Implementer handles implementation choices and executes its workstream directly. If implementation meaning is incomplete, it returns the exact material design/plan question, evidence, recommendation, and blocked consequence to the orchestrator, keeps the goal open, and resumes after the decision; the orchestrator invokes `orchestrator-design` when governing design meaning must change. The Lead does not relay every internal progress turn or poll merely to keep the conversation active, and returning to the Lead for conversation does not pause authorized implementation.
2. Admit either current reviewed design or an evidence-backed repository improvement accepted by `plan-improve-repo`. If no current ready delivery plan exists, the orchestrator loads `plan-implementation` and authors it from settled design or the admitted finding. Helpers may return repository/proof evidence only. A ready `plan-only` result reaches that requested terminal; a ready delivery plan continues immediately.
3. Commission one 🐒 Implementer and one 🔬 Verifier per workstream without automatically moving the user's conversation away from the Lead. Record real prerequisites and write collisions from the plan. Independent workstreams may run concurrently on separate execution roots; dependent ones wait until the orchestrator verifies their prerequisites. Before building, the Verifier runs the challenge branch of `verification-design` and returns a `VerifierChallenge`, and the Implementer checks that Test Design can be built. The Lead fixes a `missing-scenario` in Verification Design; a `feasibility-limit` is recorded as unverified; a `correctness-change` goes to the Lead and then to the owner, through `orchestrator-design`. If implementation or fitting proof is incomplete, the Implementer invokes `implement-plan` for its workstream and executes directly by default, using only delegation justified under `manage-agents`. It reports meaningful blockers and returns a concise source-and-proof receipt when the workstream is ready for Lead assessment; it does not send every internal progress turn through the orchestrator. The Verifier then proves the delivered behavior from the Verification Design and returns a `VerifierReport` for the head commit it tested. Direct Implementer contact remains available when the user explicitly chooses it.

   A milestone, completed slice, or phase return is a checkpoint.
4. When planned development and fitting proof are complete, the orchestrator performs the Lead assessment before any independent implementation review. Inspect the current diff and actual proof against the original need, accepted design, plan, PR scopes, and cross-PR integration. Assess from the Implementer's receipt and the `VerifierReport` for the current head commit, plus the source and evidence you open yourself. A report for an older head does not count. A report is input, never acceptance: never forward it as acceptance. Confirm required behavior is demonstrated through the right observation seams, no required work or proof is missing, boundaries and names match the design, and unnecessary complexity or unplanned compatibility machinery was not introduced. Unproven work returns to the responsible implementer for fresh affected proof. A mental-model break, public-contract change, owner decision, or plan defect stops dependent work and returns to its semantic owner. IF an implementer or reviewer reports a design break, load `../../shared-references/owner-decision-brief.md` and return the brief. Only a source-backed accepted assessment commissions the persistent independent 🔎 Reviewer through `manage-agents`, using its verified `<emoji> <role> · <purpose>` title or reporting the title capability gap.

   Return a concise source-backed assessment decision that makes the substantive inspection and outcome clear without imposing a reporting schema. A missing label alone does not invalidate adequate evidence; an assessment supported only by the implementer's summary does not authorize review.
5. The 🔎 Reviewer runs `implementation-review`. It owns detailed source reading, lane reduction, and its review result. The orchestrator checks findings against cited evidence, resolves scope or design disputes, and returns accepted implementation corrections to the implementer.
6. The same 🔎 Reviewer checks corrected code and fresh affected proof. After any correction that changes the head commit, the same Verifier refreshes the affected checks on the new head and returns a `VerifierReport` for it; inspect that current-head report before the delivery can reach readiness. A report for an earlier head never covers a corrected one. It refreshes affected coverage and applies the convergence rule in `implementation-review`'s `references/finding-and-reduction.md`. Contextual design feedback remains separate from independent review.
7. Repeat correction, proof, and review while accepted findings remain. IF the review returns `not-converging`, load `../../shared-references/owner-decision-brief.md` and return a brief of what keeps failing and why.
8. When review is ready, assign `implementation-pr-wrapup` to an 🔧 Operator or the workstream's Implementer and require current PR gate evidence back to the Lead for verification. Wait for their notifications or authorized wakes through `manage-agents`, never by model polling. Stop at PR-ready and unmerged by default. Pass through explicit merge authority only after readiness.

Record consequential decisions, accepted or rejected findings, corrections, proof outcomes, any missing-history baseline, blockers, and terminal results through `practices-show-me-your-work`. Keep logging a companion to delivery: do not create another lifecycle ledger, copied receipt store, counter protocol, or result replay mechanism.

If prior review evidence is unavailable, inspect the current source and proof boundary, record what is missing, and route an ordinary review; the current review sets the convergence baseline.

## Boundaries and Finish

- The orchestrator remains the default user conversation and owns governing design and plan authorship, planning strategy, dependencies, PR grouping, cross-PR integration, Lead assessment, acceptance, source-backed disposition, routing, and the delivery terminal. Each 🐒 Implementer directly owns bounded implementation, fitting proof, corrections, and routine mechanics for its Lead-planned workstream; the user may explicitly choose direct contact with it inside that scope. Each 🔬 Verifier owns independent proof of its workstream and its reports; it does not accept. The 🔎 Reviewer owns independent review findings and coverage. The user owns material design decisions and phase gates. PR wrap-up owns PR gate inspection.
- Verify producer results proportionally. Current scope, source, outcome, evidence, and applicable stop conditions matter; a missing label alone does not invalidate a clear result. Require exact identity when it changes correctness, including the canonical plan, reviewed diff or PR head, and source-bound proof.
- Shared work updates follow the tracker within task authority. Other external tracking remains separately authorized work and proves no delivery gate.
- On every terminal response, record the actual `complete | partial | blocked | stopped` outcome and continuation context through the tracker. Nested agents checkpoint without resolving the outer thread. Only the responsible whole-work agent checks current history and whole-work completion before resolution; render a view when requested or substantial synthesis is needed.

Open stand-ins keep a PR from `pr-ready` unless the owner accepts them, and the final report lists every open stand-in as unverified.

Completion: every material phase required by the requested terminal is currently verified—planning for `plan-only`; planning, implementation with fitting proof, a current-head Verifier report, bounded independent review and accepted corrections, and PR readiness for `pr-ready-unmerged`—or the response names the exact decision or blocker. No phase boundary, missing label, logging failure, implied merge, or continuing after `not-converging` silently changes that result.
