# Delegation examples

Inputs: the task, governing design/proof sources, actual grant and supported host. Choose the matching case, use the current Model catalog in `SKILL.md`, and return the task cut, selected model/effort, route and ending check. Examples teach boundaries; they do not add model rows or require a six-step recital.

## Collection versus interpretation

Lead needs owner decisions about review rounds from old session notes. “Tell me what the owner decided” requires interpreting authorship and adoption: pasted agent proposals are not owner decisions.

Give a Luna high Operator Exact Steps: run the named extraction procedure, return matching excerpts with file/line/context and candidate labels under supplied criteria, and mark ambiguous material. Lead opens decisive originals and determines adoption. A zero-exit scraper returning a login page reports missing content, not successful extraction. On a host without native Luna, use the supported Operator Sidekick route; do not substitute a coding model for the procedure or invent a continuing-research role.

For repeated questions about storage ownership, Lead keeps the investigation and design judgment. An Operator can collect prescribed source excerpts; it does not choose a probe or redesign storage.

## One owning pair, smaller native tasks

The design defines a search API and settings behavior. Lead supplies workstreams, the shared contract, dependencies, sequencing and completion proof. The owning Implementer reads those docs as a Designed Outcome, chooses code/test order, and works directly with its Verifier.

Use the whole assignment's real span to choose the owning Sidekicks. For a Cross-domain workstream, the current catalog allows Sol medium implementation and Sol medium verification; same-lineage verification remains a named coverage limit, never a reason to omit it. Helpers below use their own task's span:

- A Local component inside the settled interface can go to Terra high as a Designed Outcome. Give its relevant design section, write paths and ending check; inspect its changes and tests before integration.
- A separable Cross-domain change can use its corresponding implementation row. Disjoint writes may run concurrently; coupled interfaces remain with the parent or run in order.
- Prescribed log extraction or a CI watch can go to a Luna high Operator as Exact Steps. Its observations support, but do not replace, the parent's proof.

These are native tasks, not extra Implementer Sidekicks or role packets. A completed helper does not prove the settings screen uses the real search API; Implementer integrates it and the workstream Verifier observes that interaction.

## A design break versus an implementation decision

The plan requires deterministic shutdown proof, but the service exposes no completion signal. Adding a new signal changes a contract: Implementer opens the shutdown source and sends Lead the failed assumption, evidence and consequence before that change. Lead settles the contract and updates the governing design/plan. Implementer then chooses the internal event handling, test arrangement and any bounded native tasks as a Designed Outcome.

An ordinary implementation defect inside the existing contract stays with Implementer and its Verifier. They do not route each repair through Lead or redefine the expected outcome between themselves.

## Cross-system work stays integrated

Server and mobile app must change a shared price representation together. Lead settles the wire contract and release dependency. The owning implementation/verification assignment is Cross-system even when its code can be split into Local pieces. Choose the current Cross-system parent rows; Terra high may implement a bounded Local piece against the settled contract. Parent proof must exercise the actual server/app exchange and release prerequisite, not just isolated component greens.

A written contract enables decomposition; it does not erase the combined system boundary or authorize shipping one incompatible side first.

## Browser and computer-control verification

Verifier has a declared build, expected behavior and a Local or Cross-domain UI journey. Terra high is a preferred native helper when the browser/computer tools and grant exist; Sol is also preferred for control work when its listed scope/effort fits. The helper observes the real entry point and visible outcome, returning target, steps, observations, evidence and gaps. It may repair only granted verification apparatus, not product code/tests or the oracle. Use a context without authorship of that implementation.

Verifier checks the evidence, resolves reproductions/rechecks directly with Implementer, and sends its original full actionable report to Lead. Native helper completion does not replace that report.

## Independent checks sharing a fixture

Two probes reset one database and overwrite `result.log`. Their questions differ, but their effects interfere. Give them separate fixture instances/output paths through existing setup, or order them; a green result against moving state is not valid evidence. When B consumes A's artifact, wait for A's actual handback and inspect the finished artifact, not merely prompt delivery.

## Formal calls versus native tasks

Put the design, workstream, grant, pair and ending check in current governing sources. The formal live content is only:

```json
{ "role": "implementer", "files": ["docs/specs/search/plan.md", "docs/wip/search-assignment.md"] }
```

The recipient reads its role, opens current files and resolves/validates context. A Checker call selects `role: checker`; referenced sources explicitly select verification or review duty. Missing pair, duty or grant is returned before dependent work.

For a correction, select the current correction source and send role/files to the same session. Direct pair reports/reproductions keep their existing exchange contracts. A repeated call does not replay completed effects.

A parent-owned native task instead receives a bounded task/source context through the host interface with model/effort metadata. It does not enter formal role startup or acquire a role packet, separate trace or Verifier pair. The parent opens its changes/evidence and owns the combined result.

## Acceptance before outside review

After required proof, Lead opens the actual changes and original verification evidence and authors its five-condition acceptance. The outside Reviewer receives that artifact, complete scoped originals, current target and proof. Missing acceptance or an unresolved required HOLD returns review-not-started; Reviewer does not perform the missing Lead work.

Findings return for affected repair, proof, Lead acceptance recheck and affected review. Clean review starts no second wholesale acceptance ceremony. A prescribed push/watch/publish procedure may go to a Luna high Operator; readiness judgment stays with Lead and merge authority with the owner.
