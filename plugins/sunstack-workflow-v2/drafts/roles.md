# Four roles, with explicit verification and review

The role names, Luna restriction and Lead/Implementer implementation boundary are owner decisions from 2026-11-09. The owner emphasized that verification is important, then confirmed the Lead does not make the implementation changes. These are draft charters, not implemented role skills.

| Role | Starting responsibility | Does not settle |
| --- | --- | --- |
| Lead | Designs directly with the owner; keeps the goal, design, plan, integration decisions and understanding; reads code and inspects evidence before acceptance. | Does not make implementation or repair edits. Direct inspection remains its job even when code execution is assigned. |
| Checker — Verifier | Challenges proof feasibility before the build, checks whether tests establish the required outcome, observes the real target and reports evidence, failure paths and gaps. | No product repairs, fabricated observations, or treating a planned/unrun check as proof. |
| Checker — Reviewer | Independently checks original owner decisions, design, code and evidence, forming its acceptance questions before the author's completion argument. | No authoring or self-review; Router role mapping and actual verdict enforcement are still unsettled. |
| Implementer | Writes code, associated product tests, integration edits, corrections and evidence for the assigned implementation. | Governing product choices, the owner's acceptance, or self-certification as independent review. |
| Operator | Runs prescribed steps or collects under supplied criteria; returns observations and exceptions. | Architecture, implementation judgment, proof interpretation or uncommissioned repairs. |

## Models

Luna is Operator-only. It is not Lead, Checker or Implementer in v2.
For the other roles, the starting reference remains Sol or Opus for judgment, with the Lead's model chosen by the owner; availability, exact effort and a small selection table remain to be settled. Do not wake Opus while the owner's Claude-token restriction is in force.
Separate context and access to original intent matter for checking; another model lineage does not by itself make the question independent.

Proposed session arrangement: retain a Verifier through delivery and use a separate fresh Reviewer at meaningful boundaries, retaining it through corrections. The two responsibilities are explicit, but that session/lifecycle choice remains proposed. No mandatory paired-session startup or extra review of the Reviewer is selected. An explicit responsibility does not require a model to run continuously.
