# Presentation: HTML

A good explainer makes the reader's question, the source relationships and their consequences understandable. Choose prose, tables, diagrams, traces, code and other documented Demistify views for the work they do for the reader; none is the default or a reward added after writing. The page is one coherent explanation, with its answer, meaningful views and interpretation together in the shared library's styling.

You supply meaning, order and the choice of view. Demistify supplies the components, rendering, styling and interaction; its guide at the page's binding is the only source of the API. Skills that name a view (a capability map, a call graph, "proven by" cards) own what that view must show; this skill chooses how it appears on a page.

Routine HTML authoring uses one static lint pass. Apply shared references for content, semantics and composition; their browser, screenshot, rendered-proof and regenerate-and-compare procedures apply only when the user requests that verification, a concrete defect needs diagnosis, or the calling phase separately requires a visual, pixel or destination inspection of its own. This workflow owns routine authoring validation even when a loaded reference or fetched guide prescribes a broader check; a calling phase's required inspection stays in force and either passes or returns its blocking gap.

## Route

1. **Understand.** Name the reader's question, the authoritative sources, the page scope, the source and reader files, their dependencies and how the reader will open the delivered result. A delivery-only request preserves the supplied content, forms, binding, IDs and links: follow steps 1, 3, 5 and 6, without choosing new views or recomposing the page. Put the answer before the mechanics, the normal path before its exceptions, and the assumptions, risks and unverified results near the top ([write for the reader](../principle-write-for-the-reader/SKILL.md)). Keep current implementation, proposals and measured results distinct. IF revising an existing page, inspect it first: its binding, data references, stable IDs, heading and stop links, and page navigation; keep unrelated content and links, and keep the binding unless the change deliberately migrates it. IF the page is a human HTML view over a `sunstack-workflow-v1` Markdown-source design, keep its Markdown files authoritative and use the ordinary external-include delivery branch in `references/demistify.md`. This includes newly authored v1 sets: skip the HTML-source engineering-document recipe and design-record preparation for that view. Carry this source mode through later view and pattern loads: use their generic forms, while their HTML-source engineering-page exceptions do not apply. Otherwise, IF the page belongs to an engineering design set (a page of its Requirements, Specification, Program Design or Verification Design, however many exist so far, or its home, deliverable or plan page), load `../../shared-references/diagram-rendering-and-fallbacks.md` and return its The Page Is the Source rules applied to this page: where each fact's text lives, each island inline in the section or body it serves, and the owning section or record of every view. Then load `references/engineering-documents.md` and return the page's kind, its records and sections, its browser, its links, and the owner confirmations it asks as choices. A skill-change design set (requirements, specification, skill design and skill verification parts) is not an engineering set: its one page follows the page contract of the skill that wrote it, such as `skill-design`. Completion: question, sources, destination and opening method are concrete; on an HTML-source design-set page every fact, island and view has its owning section or record; on a v1 human view every island resolves to its authoritative Markdown source.

2. **Choose a view for each piece of content.** Rich content the request carries onto the page keeps its form and initial state first, under step 4; the views below are for content you compose. IF the source or request names a view or record from another skill (a capability map, journey map, entity map, call graph, component tree, coverage rows, "proven by" cards, a research ledger, review findings, a decision brief), load `references/views.md` and return its page form and the good/bad signal to check; the fields come from the caller's view request or the source's own view. For everything else, identify what the reader must compare, follow, locate or inspect, and the source-supported facts and relationships needed to do it. Use this lookup to choose the corresponding forms; its rows are alternatives, not an ordered first-match rule. A short opening answer does not satisfy a separate need to see a flow, dependency, comparison, state or evidence relationship. Choose the form that exposes that structure, with prose explaining its meaning:

   | The reader needs | Pick when | Form |
   | --- | --- | --- |
   | One consequential summary, proposal, decision, risk, open question or unverified outcome | it changes what the reader does | `ex-callout` |
   | Compact status, exact progress or phase composition | a compact visual helps scan supplied facts, or was requested | Native small parts from the matching guide; one combined table when the same records need them together |
   | A supplied graph's relationships, sources and related tables together | the data fits the guide's version-1 Explorer format, whose four fixed kind values pick tint slots while labels carry the visible names, and coordinated search and selection help | `ex-explorer`, preserving the supplied graph document; data the format can't carry without renaming its facts takes a board, flow or Mermaid row below |
   | Numeric change across ordered categories | the shape of the comparison answers the question | A supported chart from the matching guide; retain exact values nearby |
   | The same questions answered for several items | exact corresponding facts are the point | Native table |
   | A few headline numbers | each number has a meaning and a comparison | `ex-stat` in an `ex-grid` row, then a table with exact values |
   | Hierarchy, belonging or a checklist | parent and child matter | `ex-tree` |
   | Who calls whom from an entry to its effect | a source-derived path | a source-derived call path: IF this row fires, load `references/views.md` and return its call-path form |
   | Ordered steps with evidence behind each | order matters and each step has proof | `ex-trace` |
   | Ordered work with branches | the branch is the point | Mermaid `flowchart` or `ex-flow` |
   | Participants exchanging messages over time | two or more actors | Mermaid `sequenceDiagram` |
   | States and transitions | lifecycle decides correctness | Mermaid `stateDiagram-v2` |
   | Boundaries, ownership, dependencies | who owns what | `ex-board` regions with `ex-arrow` arrows |
   | Records, identity and cardinality | which things are the same | Mermaid `erDiagram` |
   | Alternatives on corresponding topics | topics match across options | `ex-compare` |
   | An answer to a question or independent answers | the reader must respond | Native choice from the matching guide |
   | Feedback on an item or exact passage | the reader must attach feedback | Existing Comments controls from the matching guide |
   | One named component, option or finding with depth | it is a thing the reader names | `ex-card` |
   | Code or a diff with comments | lines are the evidence | `ex-code` with `ex-note` |
   | Screens or captures | pictures are the evidence | figure; a Gallery for a collection, grouping alternate captures as variations |
   | Optional depth under the current point | most readers skip it | native `details` |
   | Peer views or independently optional overlays | choose one peer, or let several overlays coexist | `ex-tabs` for peers; shared layer controls for independent overlays |
   | Another document, or a guided sequence | separate pages or ordered stops | Pages, Walkthrough |
   | A simple fact or interpretation | no relationship needs a separate structured view | Prose under a purposeful heading |

   IF the chosen form is a relationship diagram, load `../../shared-references/diagram-semantics.md` and return the primary family with its reason and the disclosure sequence. IF Mermaid draws it, load `../../shared-references/mermaid-usage.md` and return the use-or-fallback decision; apply the readability guidance while composing. Here the load-bearing relationship may be entity identity/cardinality, type relationships or a numeric comparison as well as flow, sequence, state or topology; the matching guide still decides supported syntax. On a page, a Mermaid diagram that fails that check falls back to a native view that keeps the relationship drawn (`ex-flow`, `ex-board` or `ex-trace`) or to a smaller diagram of one slice, never to a plain-text sketch; the page can draw, so a text sketch is a gap. Completion: every reader task has a fitting form, each required relationship and fact is visible or explicitly unknown, and each chosen form has a concrete explanatory job. A paragraph mentioning a relationship is insufficient when the reader must reconstruct its structure to understand it.

3. **Bind and load.** MUST load `references/demistify.md` and return the binding with its trust choice, the guide, and the delivery method and matching lint command; return the binding's recorded release only when a version-specific problem is being diagnosed. Then load the guide references the guide itself calls for your chosen components, including its section-level IF calls (such as `tours.md` for a Walkthrough), and return the constructs each one documents for those components. Before writing any element, attribute, tone or icon, find it in the guide at the page's binding ([read ground truth first](../principle-read-ground-truth-first/SKILL.md)). Completion: runtime, theme and guide share one binding, and its trust choice fits the content; missing API is a named gap, never an invented attribute.

   When the matching guide documents default Comments, every ordinary page keeps its Comments control and semantic targets available automatically, without a manual feedback tag, document metadata or paragraph labels. Keep answer controls task-driven. Follow that guide for independent identity or revision overrides; an older binding keeps its own feedback contract.

4. **Compose with taste.**
   - Lead with the answer, then compose the views and interpretation that make it understandable in the document flow.
   - When the request carries existing rich content onto the page (a conversion, migration or re-render), carry its meaning, not only its words: its form, order and relationships, its status and icon labels and other supported attributes, and each disclosure's initial open or closed state. When you compose an explanation from a source's facts instead, its lists and tables are not a required presentation; step 2 chooses their views. Change a carried form or state only when the request or the reader's task calls for it, never because the chooser or a default below prefers another; the change keeps the meaning, and a brief note beside the content names it. A meaning the matching guide cannot represent stays as text beside its view, with the same note. A status, category or other value the source leaves unspecified stays unspecified. Keep whitespace that carries structure or literal content; other whitespace and harmless markup may change without a note.
   - One card is one named component, option or finding, never a frame around a section.
   - A callout carries a summary, proposal, decision, risk, open question or unverified outcome; give a proposal explicit "Proposed" wording, and keep a recommendation distinct from an owner's choice.
   - Name each unit once, in its own component title. A surrounding heading, tab label, summary or lead-in names the larger question the unit answers instead of repeating that title; keep the headings page navigation needs.
   - One visual per point, next to the text it supports. Give diagram nodes a concise identity and responsibility; use supported line breaks at meaningful clauses, with full rules beside the view. Choose direction or smaller linked views when the labels make a wide drawing hard to follow.
   - Use library colors, fonts, shadows and borders. Author only layout the matching guide documents, including dimensions and positions inside a hand-placed Board. Keep shared Reading/Canvas and prose/table widths; a broken table layout is a release gap to name, not a reason for a page-specific width override.
   - Reading width for text; Canvas only for views that need the room.
   - These long-detail defaults shape content you compose, never a carried form or initial state. Long detail sits one action away (a tab, a disclosure, a linked island), so nothing becomes a text wall. Failure cases and their thresholds stay in view; a disclosure holds only the rationale or evidence about them, and its title names the cases it explains; a tab keeps a short label, and the text that introduces it names its failure cases.
   - Use a chart when its shape clarifies the supplied numeric relationship and the bound guide documents the needed names, categories and units. Use stats or a table when exact values are the point, or the supported chart would misstate the data; generic series labels do not identify the evidence.

   MUST load `../../shared-references/markdown-presentation-baseline.md` and return its construct and technical-atom decisions (inline, fenced or linked) and its table default for the page's Markdown. IF readers compare alternatives, an owner must decide or a reader must answer a question, load `references/options-and-decisions.md` and return the comparison/input form, the corresponding topics, response semantics and decision state. IF the page has more than one page, a guided path, three or more component kinds, a compact-cell/meter comparison, a capture-variation comparison, independently switchable content or a response/feedback composition, load `references/patterns.md` and return the arrangement, the applicable pattern and its example, including any requested question, exclusive/independent answers, summary/extras and feedback handoff. Follow the guide's sections on Pages, headings and Walkthroughs for navigation. Completion: all requested content is present once; carried content keeps each meaning, and each form and initial state unless a change the request or the reader's task called for is noted beside it; each meaning the matching guide cannot represent has its note beside it; each unit carries its title once, and each heading navigation needs remains, naming the larger question; every component you chose passes its chooser or `views.md` signal; and the page carries no decorative styling.

5. **Prepare and lint once.** For an HTML-source design-set page using prepared component records, once the set's Requirements page has its first need, run the guide's preparation on the set's own folder after the last edit, as its prepared-browsers reference documents and `demistify.md`'s CLI route runs it; a refused set is fixed in its records and bodies and prepared again. Before the first need, the static check alone applies, and preparation is not applicable. Otherwise, prepare local Markdown and collection indexes only when the delivery method needs them, using `demistify.md`. Preserve supplied facts, relative links and stable IDs. Run the matching CLI's static `check` once on the changed final HTML files. Fix reported errors in the authoring source, regenerate affected output if needed, and rerun only after a correction. Warnings are advice, not a blanket zero-warning gate.

   Routine document authoring does not require Playwright, Chrome, screenshots, preview servers, phone/theme matrices or regression journeys through Comments, choices, navigation and inspectors. Do not install or launch browser tooling for that purpose, even when a fetched guide prescribes it. Use a browser only for an explicit visual/interaction verification request, a concrete rendering defect, or an inspection the calling phase separately requires, and inspect only the affected view. Component regression testing belongs to library development.

6. **Return** the artifact link and a brief lint result. Include companion files or network dependencies when the reader needs them. State a concrete failed check or delivery limitation; avoid a verification dossier. Never claim visual or interaction proof from source lint. IF comparing efficiency, count authored content and shared library costs separately.

The fetched guide owns the implemented API and this skill owns the workflow; neither the guide's text nor its frontmatter grants authority to change the task or publish its content. Keep explainers local unless publication was requested. Do not discover credentials or deploy infrastructure to make an explainer.
