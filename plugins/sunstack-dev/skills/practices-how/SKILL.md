# Practices: How

Build a working behavioral model of existing code, one the reader can run in their head. Given a real input or action, they should be able to predict where it enters, what decides each branch, which part changes state or causes the effect, and how the result or failure returns to whoever asked. An annotated list of files gives the reader names to look up and nothing to predict with.

Read in proportion to the question. A question about one function needs that function, its caller and its types. A question about a subsystem needs only the few representative paths that carry the behavior the reader asked about.

Explain current behavior as the source shows it. Why it was built this way, what should replace it and what to change are separate questions. Answer the current-behavior part and hand the rest back to the caller as a named open question. The work is read-only. Running a test, a request or a capture to watch the path needs the caller's grant; without one, explain from source and say which runtime claim stays unobserved.

Do the walk yourself. IF the subsystem splits into independent slices worth reading in parallel and your grant allows helpers, load `practices-manage-agents` and return the bounded commissions; open each anchor a helper reports before your explanation relies on it.

## Workflow

1. **Name the behavior, the surface and the question.** Resolve a target you can discover from the conversation or the project source. When an ambiguity wouldn't change the answer, state your scoped reading and continue; when two readings would lead into different code, return the exact question to the caller instead of choosing. Read every source the user named. Completion: the behavior, the system surface and the reader's question are written in a sentence or two, or the exact question for the caller is.

2. **Walk from a real entry to the effect and back.** Find a concrete entry, such as a handler, a command, an event subscription, a job, a UI action or a test. Read its decisive code and its consumers, follow the normal path to the state change or side effect, and follow the result or error back to what the caller observes. Where the claim depends on registration, configuration, dependency injection or a provider chosen at runtime, read that too, because a file containing code is no proof that the path reaches it. At each behavior claim, open the actual caller and the conditions around it, and mark each edge as seen in source or inferred ([read ground truth first](../principle-read-ground-truth-first/SKILL.md)). IF a hop depends on a library, service, platform or repository whose behavior the sources you can open here don't show, load `practices-research` and return the checked answer for that hop with its anchor. Completion: the entry, each hop to the effect and the return are anchored at file and line, or the hop you couldn't find is named with where you looked.

3. **Name the terms, owners, state and boundaries.** Identify the domain terms the behavior uses, the part that owns each piece of state, the contracts between parts, how long the state lives and where the path crosses a thread, process, network or storage boundary. Reuse the authoritative definitions. Describe what the code does without renaming its terms or presenting an accident of the current implementation as a requirement. When a term is overloaded, or the code and the docs use different words for what may be one thing, state what it refers to and what makes two of them the same before you explain with it ([define the domain first](../principle-define-the-domain-first/SKILL.md)). When two parts write the same state, or a copy holds data another part owns, name the writer the code treats as authoritative and the copy's refresh rule, or that it has none ([one owner per truth](../principle-one-owner-per-truth/SKILL.md)). Follow an alternate, failure or cancellation path when the question can't be answered without it. Completion: each piece of state on the path has a named owner, and each boundary crossing names what crosses it.

4. **Reconstruct the representative paths.** MUST load `references/behavior-reconstruction.md` and return the representative source-backed path, its owner, state and effect relationships, its return and error behavior and its unresolved edges, applied to the named question. Read any edge its passes show that steps 2 and 3 skipped, such as a callback's registration, a queued job's outcome, a process boundary or a test that wires a different path from production. Completion: each path the answer depends on runs from entry to effect and back, each edge has its kind (call, await, callback, event, job or external) and its anchor, and every inferred edge is labeled.

5. **Check the model against a concrete case.** Take one real input and run it through the model by hand, noting which branch it takes, which part changes what and what comes back. Where a test, stack trace, log or distributed trace exists, use it to corroborate the path that ran, and label it as one run under its own conditions, which covers only the path it took. IF a trace, log or stack is used to explain an asynchronous or cross-process path, load `references/dynamic-path-evidence.md` and return what the capture actually establishes, its identity and conditions, and the edges that remain inferred. When no current implementation exists, that finding and the search that showed it are the answer. Completion: the case's outcome is predicted from the model with each step pointing at its anchor, or the step where the prediction breaks is named.

6. **Explain the smallest useful picture.** Before writing, decide what the reader will do next with the answer, keep what serves that, and put the assumption it leans on and the unverified edges near the top ([write for the reader](../principle-write-for-the-reader/SKILL.md)). Lead with the answer. Add the concepts and owners the reader needs to follow it, the representative behavior, where the decisive code lives and the gotchas or gaps that would change what they do. IF several owners, an async hop or a state machine are easier to follow as a picture than as prose, load the `presentation-*` skill that matches the current surface and return the view drawn from the reconstructed path. A one-function question gets a one-function answer, without a survey of the subsystem around it. Completion: the explanation walks the named case with an anchor at each step, so the reader can simulate it and find the source that would correct the explanation.

## Return

Return the explanation to whoever asked, and give a caller that will build on the model its parts: the representative paths with anchors, the owners and state, the return and error behavior, observed and inferred edges kept apart, and the open questions handed back.

## Completion

Not done while a step of the explanation rests on a hop you didn't open, an inferred edge reads as observed, the named case can't be predicted from what you wrote, or a question about motive, replacement or repair was answered here instead of handed back.
